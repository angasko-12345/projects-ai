The dry-run is not an experiment and produces no benchmark number. It installs the pinned
stack, downloads the real datasets, tokenises with the real LFM3 tokenizer and trains a
randomly initialised tiny model for three steps to prove the TRL/PEFT wiring. It exists
because the GPU job it protects is expensive and the account has ~9 GPU-hours left.

## Why the GPU work has not produced numbers yet

Free-tier GPU queue latency. Both baseline kernels have been `QUEUED` for an extended period
while a CPU kernel dispatched immediately, so this is worker availability rather than a bug.
Quota is charged when a session runs, not while it waits. Details and mitigation in
`BLOCKERS.md` B-01.

A second, self-imposed limit: the account allows at most two concurrent GPU sessions
(`Maximum batch GPU session count of 2 reached`), which is why the third and fourth kernels
cannot be pushed until a slot frees (`DECISIONS.md` D-12).

## Order of work from here

1. Read the dry-run report; fix anything it catches while the GPU queue drains.
2. When a baseline finishes, `py -3.12 tools\fetch_results.py` (sha256 manifest per artifact),
   then `py -3.12 tools\report.py --inputs results --out .`.
3. Push the SFT kernel, then evaluate the adapter on the same frozen suite.
4. Push the Qwen3.5 planner once a GPU slot frees.
5. Fill `experiments/*/README.md` and `MODEL_REGISTRY.md` conclusions with measured values only.

## Standing constraints still in force

- Every model runs on Kaggle. The Windows host never loads weights; local Python is limited to
  parsing tests and report generation.
- No synthetic training data in this milestone; public, licence-declared datasets only.
- The held-out suites are never used for training or hyperparameter choice.
- Private notebooks and a private dataset; no credential is stored, printed or committed.
- Nothing is staged, committed or pushed to Git without explicit authorization.
